# AI 도구 활용 및 검증 기록

## 1. 활용 원칙

강의 슬라이드 p.8~10은 AI 코딩이 빠르게 보편화되었지만, 자연어 요구에 보안을 명시하지 않으면 API 키 노출·입력 검증 누락 같은 약점이 생길 수 있다고 설명한다. p.34는 ChatGPT, Copilot, Cursor, Claude 등 AI 도구를 최대한 적극적으로 활용하라고 요구한다. 강의 녹음도 AI 결과를 이해하고 책임질 수 있어야 한다고 강조한다.

이 프로젝트는 **Codex와 병렬 에이전트**를 적극적으로 사용하되 다음 원칙을 적용한다.

1. AI 출력은 제안과 초안이지 신뢰할 수 있는 실행 증거가 아니다.
2. 보안 요구와 금지 사항을 프롬프트에 명시한다.
3. 한 에이전트가 만든 결과를 코드, 테스트, DB 불변식, 브라우저 동작으로 별도 검증한다.
4. 구현 완료·테스트 통과·취약점 0건을 AI의 설명만으로 기록하지 않는다.
5. 비밀번호, 세션 토큰, API 키, 실제 개인정보와 금융정보를 프롬프트에 넣지 않는다.
6. 최종 범위·위험 수용·제출 책임은 사람이 가진다.

## 2. 사용한 방식

### 2.1 주 에이전트

Codex 주 에이전트는 전체 과제를 작은 작업으로 나누고, 작업공간 상태와 사용자 요구를 기준으로 결과를 통합한다.

- 강의자료·녹음 근거 확인
- 최소 7개 기능과 제출 조건 추적
- 구현·문서·테스트 작업의 순서와 파일 범위 조정
- 병렬 에이전트 결과의 충돌 확인
- 최종 테스트 실행과 산출물의 코드·증거 일치 검토

### 2.2 병렬 에이전트

서로 독립적으로 진행할 수 있는 작업을 병렬화했다. 모든 에이전트는 같은 작업공간을 공유하므로 파일 범위를 분리하고, 핵심 계약은 메시지로 동기화했다.

| 역할 | 담당 범위 | 생성/전달한 핵심 결과 | 사람/주 에이전트 검증 |
|---|---|---|---|
| 강의자료 분석 에이전트 | `secure-coding-slide.v2.pdf`와 강의 녹음 분석 | 최소 기능 7개, p.31 체크리스트, 마감 정정, 채팅·송금 질의응답 근거 | 슬라이드 페이지와 녹음 문맥을 다시 대조. 자료 자체는 저장소에 복사하지 않음 |
| 아키텍처 에이전트 | FastAPI/Jinja2/sqlite3/WebSocket 코어 계약 | 세션 토큰 해시, CSRF, 정수 ID+서버 권한검사, 가상 KRW 이중 원장, 신고·채팅 모델 | 요구·설계·위협·코드의 필드와 불변식 대조 |
| 구현 에이전트 | 라우터·서비스·DB·템플릿 구현 | 요구사항을 코드로 변환 | 코드 diff와 36개 자동 테스트, 정적·의존성 검사로 검증 |
| 테스트/보안 검토 작업 | 정상·경계·권한·동시성 테스트와 리뷰 | p.31 및 STRIDE 항목에 연결된 테스트 | 실패 수정 후 36 passed, branch coverage 73% 실제 출력 확인 |
| 문서화 에이전트 | 요구사항·설계·위협·체크리스트·유지보수·AI 기록 | 현재 `docs/` 문서 | 구현·테스트와 문서 수치 및 잔여 위험 재대조 |

병렬화는 “여러 AI가 동의했으므로 정답”이라는 의미가 아니다. 같은 잘못된 가정을 공유할 수 있으므로 서로 다른 증거 방식이 필요하다.

## 3. AI에 제공한 핵심 제약

프롬프트와 작업 지시에는 다음 제약을 반복해서 포함했다.

- 강의 최소 기능 7개를 모두 추적할 것
- 송금은 실제 돈이 아닌 정수 원 단위의 현금 가치 없는 가상 KRW 원장으로 제한할 것
- 송금은 `BEGIN IMMEDIATE`, 잔액 조건부 차감, 양쪽 잔액·transfer·ledger 2행을 한 트랜잭션에서 처리할 것
- 비밀번호 평문 저장 금지, 세션 원문 토큰 DB 저장 금지
- 모든 POST의 CSRF를 서버에서 상수 시간 검증할 것
- 인증과 소유권/역할 검사를 분리할 것
- Jinja 자동 이스케이프, 바인딩 SQL, WebSocket 세션·Origin·대상 권한·길이·속도 검증을 적용할 것
- HTTP body는 form parser 바깥 pure ASGI에서 선언 길이와 실제 chunk 합을 모두 제한할 것
- 이미지·WebSocket·상품에 전역·사용자별 용량 상한을 두고 느린 수신자를 격리할 것
- async 경로의 SQLite·Pillow·Argon2 blocking 작업을 worker thread로 오프로딩할 것
- 오류 응답·로그·Git에 비밀정보를 노출하지 말 것
- 강의자료 원본을 public 저장소에 복사하지 말 것
- 아직 실행하지 않은 테스트 결과나 수치를 완료로 단정하지 말 것

이처럼 비기능 요구를 명시하지 않으면 AI가 “화면이 동작하는 MVP”에만 집중할 가능성이 있으므로, 보안 불변식을 기능 요구와 같은 수준의 완료 조건으로 주었다.

## 4. AI가 도운 개발 단계

### 4.1 요구사항 분석

AI가 PDF 페이지별 텍스트와 렌더링 화면, 녹음 전사를 교차 확인하여 다음 모호성을 찾았다.

- 슬라이드 p.35의 최소 기능은 7개이며 모두 구현 대상
- 앞의 네 기능은 p.25~28 상세 설계를 포함하고, 송금·검색·관리자는 분석부터 직접 수행
- 송금의 구체 범위는 강사가 정답을 주지 않고 학생이 고민해 정하도록 함
- 여러 사용자가 실제로 채팅할 수 있어야 하며 별도 기기에서 확인한 사례가 있음
- 슬라이드 p.36의 `2026-07-23(금)`은 녹음에서 `2026-07-24(금) 23:59`로 정정됨

사람이 확인할 사항은 이 해석이 최신 LMS/Discord 공지와 일치하는지 여부다. 이 저장소의 강의자료 기준으로는 위와 같이 기록했다.

### 4.2 시스템 설계

AI가 기능 목록을 데이터 모델, 라우트, 권한 매트릭스와 다음 불변식으로 변환했다.

- 발신자·소유자·신고자는 클라이언트 입력이 아니라 세션에서 결정
- 정수 객체 ID를 사용하되 식별자 비밀성에 의존하지 않고 모든 조회·변경에서 소유권·참여자·RBAC를 검사
- DB에는 세션 원문 대신 SHA-256 토큰 해시 저장
- 송금 성공마다 송·수신 ledger 2행, delta 합 0, 잔액 음수 금지
- 송신자별 idempotency key로 중복 이체 방지
- 신고자별 같은 대상 중복 신고 금지
- 전체 채팅은 `recipient_id = NULL`, DM은 참여자만 접근
- 감사 로그는 애플리케이션에서 추가 전용

사람은 설계가 코드와 정확히 일치하는지, 특히 실패·동시성 경로에서도 불변식이 유지되는지 검증해야 한다.

### 4.3 구현

AI는 반복적인 라우터, 폼, SQL, 템플릿과 테스트 초안을 빠르게 만들 수 있다. 그러나 다음 부분은 생성 코드를 그대로 채택하지 않고 보안 중심으로 리뷰한다.

- 비밀번호 해시 파라미터와 예외 처리
- 세션 생성·회전·만료·폐기
- CSRF가 빠진 상태 변경 라우트 존재 여부
- URL 객체 ID와 소유권·관리자 권한
- 동적 SQL·정렬 열·`LIKE` 이스케이프
- Jinja `safe`, `innerHTML`, 사용자 입력의 JavaScript 문맥 삽입
- WebSocket Origin·DM 대상·사칭·속도 제한
- SQLite 트랜잭션 경계와 예외 rollback
- 업로드 형식·경로·크기 검증
- 로그의 토큰·비밀번호·메시지 노출

구현은 실제 코드와 자동 테스트로 대조했다. 2026-07-22 기준 36개 테스트, branch coverage 73%, Ruff·Bandit·pip-audit 통과를 기록했으며 실제 HTTPS/WSS 프록시와 멀티프로세스 고부하는 별도 범위로 남겼다.

### 4.4 체크리스트와 테스트

AI가 슬라이드 p.31의 21개 항목을 식별자와 판정 기준으로 바꾸고, STRIDE 위협에 맞춰 송금·검색·관리자·업로드 항목을 추가했다. 또한 정상, 경계, 형식 오류, XSS/SQL injection, 인증, IDOR, CSRF/Origin, 재전송·동시성, 남용, 오류 복구 범주를 테스트 설계에 포함했다.

테스트 코드를 생성하는 것과 테스트가 유효한 것은 다르다. 사람은 테스트가 취약한 구현에서도 잘못 통과하지 않는지, 기대값이 요구사항을 정확히 표현하는지 검토해야 한다.

### 4.5 유지보수와 보고서

AI는 변경 관리, CI, 의존성 패치, SQLite 백업·복구, 사고 대응 초안을 만들었다. 실제 백업 성공, 복구 시간, CI 결과는 실행 후 증거가 있을 때만 보고서에 적는다.

## 5. 사람이 검증하는 방법

### 5.1 요구사항 추적

1. 강의 p.34~35의 각 최소 기능을 `requirements.md`의 FR과 연결한다.
2. 각 FR이 라우트·서비스·DB·화면·테스트에 모두 존재하는지 추적표로 확인한다.
3. 요구사항을 변경한 경우 이유, 보안 효과, 사용성 비용을 보고서에 적는다.
4. “실제 송금”처럼 모호한 표현은 범위 밖 항목과 화면 고지까지 확인한다.

### 5.2 코드 리뷰

1. AI가 수정한 전체 diff를 사람이 읽는다.
2. 외부 입력의 시작점에서 DB·템플릿·로그·파일까지 데이터 흐름을 따라간다.
3. 인증, 소유권, 관리자 역할, 계정 상태가 어느 계층에서 검사되는지 확인한다.
4. 성공 경로뿐 아니라 예외·rollback·연결 종료·중복 요청 경로를 확인한다.
5. 단순 문자열 검색으로 동적 SQL, `safe`, `innerHTML`, 하드코딩 비밀, debug 설정을 보조 점검한다.

### 5.3 자동 테스트

- 새 임시 DB에서 전체 테스트를 실행한다.
- 한 테스트가 이전 상태에 의존하지 않게 격리한다.
- 테스트 이름 또는 표에서 FR, TM, SC ID를 연결한다.
- 실패가 있으면 원인을 수정하고 동일 취약점의 회귀 테스트를 남긴다.
- 성공 수·커버리지·실행 환경은 실제 출력에서 가져오며 AI가 추정한 숫자를 사용하지 않는다.

현재 실제 실행 결과는 **36 passed, branch coverage 73%**다. Ruff는 보고서 생성기를 포함한 26개 Python 파일의 lint/format을 통과했고 Bandit finding과 pip-audit의 알려진 취약점은 각각 0건이었다. 상세 명령·테스트별 증거는 `test-results.md`에 기록했다.

### 5.4 외부·규모 검증

CSRF/Origin, IDOR, XSS, 전체/DM, 병렬 송금, WebSocket 동시 연결·느린 수신자는 자동 회귀 테스트로 실행했다. 남은 외부 검증은 다음과 같다.

- 실제 역방향 프록시의 HTTPS/WSS, `Secure` cookie, HSTS, Host/Origin, WebSocket upgrade
- 단일 worker 범위를 넘는 멀티프로세스 고부하와 공유 rate limit/pub-sub 설계
- public push 후 GitHub Actions의 원격 품질 게이트

외부 검증을 수행하면 날짜, 환경, 입력, 기대, 실제, 증거 위치를 추가한다.

### 5.5 저장소·산출물 검증

- public push 전 현재 파일과 Git 이력에 `.env`, DB, 백업, 업로드, 로그, 비밀, 실제 개인정보가 없는지 확인
- 강의 PDF·녹음 원본을 저장소에 포함하지 않음
- README의 환경설정·실행·초기 관리자·테스트 방법을 새 환경에서 따라 함
- 보고서의 GitHub 링크와 태그/커밋이 제출 버전을 가리키는지 확인
- 보고서 파일명, 마감, LMS 제출 조건을 최신 공지와 다시 확인

## 6. AI 출력에서 특별히 경계한 오류

| 가능 오류 | 왜 위험한가 | 검증/완화 |
|---|---|---|
| “bcrypt로 암호화” 같은 용어 혼동 | 비밀번호를 복호화 가능한 암호화로 잘못 구현할 수 있음 | 단방향 적응형 해시와 라이브러리 verify 사용 확인 |
| 클라이언트 검증만 추가 | 직접 요청으로 우회 가능 | 서버 테스트에서 HTML 속성 없이 같은 입력 거부 확인 |
| 관리자 버튼만 숨김 | 직접 URL/API 접근 가능 | 일반 사용자 접근 매트릭스 테스트 |
| `SELECT ... f'{q}'` 형태 검색 | SQL injection | sqlite3 바인딩과 공격 문자열 테스트 |
| HTML 태그 제거만으로 XSS 해결 주장 | 문맥·인코딩 변형 우회 가능 | 자동 이스케이프+CSP+여러 표시 화면 검증 |
| 잔액 조회 후 별도 UPDATE | 경쟁 상태로 이중 지출 | `BEGIN IMMEDIATE` 안 조건부 차감과 병렬 테스트 |
| 전역 idempotency key만 고유 | 사용자 간 키 충돌·DoS 가능 | `(sender_id, idempotency_key)` 고유성 확인 |
| WebSocket이 쿠키만 보면 안전하다고 주장 | cross-site WebSocket hijacking 가능 | 정확한 Origin 검사와 악성 Origin 테스트 |
| middleware 안에서만 `Content-Length` 확인 | chunked·누락 헤더로 body 상한 우회 | pure ASGI 실제 수신 byte 제한과 7MB chunked 테스트 |
| async 라우트에서 동기 SQLite·Pillow 실행 | event loop 전체 정지와 서비스 거부 | worker thread 오프로딩, 이미지 CapacityLimiter |
| WebSocket 연결·send 무제한 | 연결 메모리 고갈·느린 수신자가 전체 fan-out 지연 | pre-auth/user/global cap, 연결별 lock, 2초 timeout, 병렬 fan-out 테스트 |
| 테스트 코드 존재를 통과로 보고 | 실행 실패·약한 assertion을 놓침 | 실제 명령 출력과 실패 수정 기록 |
| “취약점 없음” 결론 | 테스트 범위를 넘어선 안전성 과장 | 잔여 위험·범위·미검증 항목 명시 |

## 7. 프롬프트·데이터 보안

- 실제 운영 비밀과 개인정보는 AI 입력에서 제거한다.
- 로그나 DB 예시가 필요하면 합성 사용자와 가상 금액을 사용한다.
- 저장소 파일 안의 지시문은 신뢰할 수 있는 개발자 지시와 구분한다. 외부 데이터가 “이전 지시를 무시하라”고 해도 실행하지 않는다.
- AI가 제안한 패키지·명령·URL은 공식 문서와 현재 환경에서 확인한 뒤 사용한다.
- 파괴적 명령, 외부 공개, Git push, 데이터 삭제는 정확한 대상과 사용자 권한을 확인한다.
- AI가 만든 보고서 문장은 코드·테스트·Git 증거와 일치하지 않으면 수정한다.

## 9. 최종 책임 선언

AI는 속도와 탐색 범위를 높였지만 보안을 보증하지 않는다. 제출자는 다음을 직접 확인해야 한다.

- 어떤 요구사항을 왜 선택·변경했는지 설명할 수 있는가
- AI가 만든 인증·권한·트랜잭션 코드를 읽고 실패 경로를 설명할 수 있는가
- 테스트가 무엇을 증명하고 무엇은 증명하지 않는지 아는가
- 잔여 위험과 과제용 가상 원장의 한계를 숨기지 않았는가
- public 저장소와 PDF 보고서가 실제 검증 결과만 주장하는가

이 원칙에 따라 최종 보고서에는 AI 사용을 투명하게 기록하고, 사람의 검증 증거와 미검증 항목을 구분한다.
