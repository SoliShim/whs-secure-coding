# 요구사항 분석

## 1. 문서 목적과 근거

이 문서는 **Tiny Second-hand Shopping Platform**의 구현 범위와 검증 가능한 인수 조건을 정의한다. 기준은 강의 슬라이드 p.22~35와 강의 녹음의 과제 설명 및 질의응답이다.

- 슬라이드 p.22~23: 중고거래 플랫폼의 기능·비기능 요구사항 도출
- 슬라이드 p.24~28: 앞의 네 기능(가입, 상품, 소통, 악성 사용자·상품 차단)의 상세 설계 예시
- 슬라이드 p.30~33: 요구사항·기능·보안 체크리스트, 테스트 케이스, 유지보수
- 슬라이드 p.34~35: 과제 범위와 최소 기능 7개
- 강의 녹음: 아래 7개 기능은 모두 구현해야 하며, 송금·검색·관리자 기능은 요구사항 분석부터 직접 진행하고, 합리적인 변경은 이유를 보고서에 남기면 허용된다고 설명

강의 슬라이드 p.35의 “24page에서 명세한 것을 모두 포함”이라는 표기는 앞의 상세 설계 예시(p.25~28)를 가리키는 것으로 해석한다. 따라서 최소 7개 기능만 이름만 갖춘 형태가 아니라, 상세 기능과 보안 통제까지 포함한다.

## 2. 목표

가입한 사용자가 상품을 등록·검색·열람하고, 다른 사용자와 실시간으로 대화하고, 안전한 데모용 잔액을 송금할 수 있는 작은 중고거래 웹 플랫폼을 만든다. 신고와 관리자 검토를 통해 악성 사용자·상품을 통제하며, 개발 전 과정에서 서버 측 입력 검증과 권한 검사를 적용한다.

## 4. 핵심 범위 결정: 송금 기능

### 4.1 변경한 요구사항

강의의 “유저들 간의 송금”은 **실제 원화 결제나 은행 송금이 아닌, 현금 가치가 없고 과제 환경 안에서만 사용하는 가상 KRW 원장 이체**로 구현한다.

- 단위는 `KRW`로 표시하지만 모든 금액은 정수 원 단위로 저장한다.
- 실제 카드 번호, 계좌 번호, 주민등록번호, 본인인증 정보는 수집하지 않는다.
- 충전·출금·환전·외부 결제대행사 연동은 제공하지 않는다.
- 일반 회원가입 계정의 데모 초기 잔액은 `users.wallet_balance`에 `100,000 KRW`로 직접 설정한다.
- 현재 초기 지급에 대응하는 genesis/funding 원장 항목은 만들지 않는다. 따라서 원장은 계정 생성 시점부터의 전체 잔액 출처가 아니라, 사용자 간 이체 이후의 변동을 추적한다.
- 사용자 간 이체에서는 잔액, 이체 기록, 송·수신 원장 2행을 하나의 트랜잭션으로 갱신한다. 실제 회계 시스템으로 확장할 때는 초기 지급도 명시적인 genesis/funding 거래로 기록하고 전 잔액을 원장과 조정해야 한다.

### 4.2 변경 이유

실제 금융 기능은 전자금융 관련 법적·운영적 요구, 결제대행사 계약, 실명확인, 부정거래 탐지, 키 관리와 높은 수준의 가용성을 요구한다. 과제용 단일 서버에서 이를 흉내 내며 실제 결제정보를 받는 것이 오히려 새로운 고위험 자산을 만든다. 가상 원장은 “사용자 간 가치 이전, 잔액 부족, 중복 요청, 동시성, 권한, 감사 가능성”이라는 송금의 핵심 보안 문제를 안전하게 학습하면서도 불필요한 개인정보·금융정보 수집을 피한다.

## 5. 기능 요구사항

인수 조건의 판정은 `통과`(자동 테스트로 핵심 조건 확인), `부분 통과`(구현되었으나 조건 일부만 자동 확인), `미검증`(실제 환경 또는 별도 리허설 필요)로 구분한다. 현재 기준 실행 결과는 `pytest` 36개 통과, 분기 커버리지 73%다.

### FR-01 회원가입·로그인·프로필

- 사용자명은 중복될 수 없으며, 길이·문자 집합을 서버에서 검증한다.
- 비밀번호는 정책을 만족해야 하고 검증된 비밀번호 해시로만 저장한다. 평문 및 복호화 가능한 형태로 저장하지 않는다.
- 로그인 성공 시 서버 측 세션 또는 서명·보호된 세션 식별자를 사용한다.
- 사용자는 다른 사용자의 공개 프로필을 볼 수 있고, 본인의 소개글과 비밀번호를 변경할 수 있다.
- 비밀번호 변경 등 민감 작업에는 현재 비밀번호 재확인을 요구한다.
- 정지된 계정은 보호된 쓰기 작업과 WebSocket 접속을 사용할 수 없다.

**인수 조건**

1. 유효한 정보로 가입·로그인하고 세션을 발급·폐기할 수 있다. **부분 통과** — 가입·로그인과 비밀번호 변경에 따른 세션 폐기는 자동 검증했으나, 명시적 로그아웃 후 세션 재사용은 별도 자동화하지 않았다.
2. 중복 사용자명과 서버 입력 정책 위반을 거부한다. **부분 통과** — 중복 가입은 `test_duplicate_registration_and_login_failure_are_safely_reported`로 확인했으나 모든 문자·길이·약한 비밀번호 경계 조합은 자동화하지 않았다.
3. DB에는 Argon2id 해시와 세션 토큰의 SHA-256 해시만 저장하고 로그인 오류를 일반화한다. **통과** — `test_registration_uses_argon2_and_stores_only_session_hash`, `test_duplicate_registration_and_login_failure_are_safely_reported`
4. 프로필·비밀번호 변경 대상은 URL/폼 ID가 아니라 현재 세션 사용자로 고정한다. **통과** — `test_profile_update_escapes_output_and_password_change_revokes_all_sessions`

### FR-02 상품 등록·열람·관리

- 인증된 사용자는 상품명, 설명, 가격, 사진을 포함한 상품을 등록할 수 있다.
- 목록에는 핵심 정보가 표시되고 상세 화면에서 설명, 가격, 사진, 판매자 정보를 볼 수 있다.
- 공개 상태의 상품은 비회원도 열람할 수 있다.
- 판매자는 자신이 등록한 상품만 수정·판매완료·삭제할 수 있다.
- 상품 가격은 0보다 큰 정수 원 단위이며 상한을 둔다.
- 이미지 업로드를 제공할 경우 허용 형식, 실제 파일 시그니처, 크기, 픽셀 수를 검증하고 서버가 생성한 파일명으로 저장한다. 업로드하지 않으면 안전한 기본 이미지를 표시할 수 있다.

**인수 조건**

1. 정상 상품의 등록·목록·상세 흐름과 이미지 저장이 동작한다. **부분 통과** — `test_product_upload_is_reencoded_and_user_content_is_escaped`; 본인 수정·삭제의 전체 정상 흐름은 자동화하지 않았다.
2. 다른 사용자의 상품 수정·삭제는 거부한다. **통과** — `test_non_owner_cannot_edit_or_delete_product`; 비회원은 인증 의존성으로 보호한다.
3. 가격·본문의 서버 범위 검증을 구현했다. **부분 통과** — 이미지/요청 본문 크기 경계는 자동 검증했으나 가격의 모든 음수·소수·상한 조합은 자동화하지 않았다.
4. 상품명·설명 HTML은 템플릿에서 이스케이프된다. **통과** — `test_product_upload_is_reencoded_and_user_content_is_escaped`

### FR-03 사용자 간 소통

- 로그인 사용자는 전체 채팅방에서 실시간으로 대화할 수 있다.
- 로그인 사용자는 특정 사용자와 1:1 대화를 할 수 있다.
- 메시지 발신자는 세션으로 결정하며 클라이언트가 보낸 발신자 ID를 신뢰하지 않는다.
- 메시지 길이, 형식, 수신자 존재 여부, 계정 상태를 서버에서 검증한다.
- 짧은 시간의 과도한 메시지는 속도 제한으로 차단한다.
- 강의 녹음에서 여러 사용자가 실제로 채팅할 수 있어야 하며, 강사가 서버와 별도 휴대폰으로 확인한 사례가 언급되었다. 따라서 같은 브라우저 안의 모의 채팅이 아니라 서로 다른 클라이언트가 접속 가능한 WebSocket 기능을 목표로 한다.

**인수 조건**

1. 서로 다른 세션의 전체 채팅과 1:1 채팅, nonce 중복 방지가 동작한다. **통과** — `test_websocket_global_dm_nonce_deduplication_and_length_validation`
2. 비인증·잘못된 Origin·CSRF로 연결할 수 없고 발신자는 세션에서 정한다. **부분 통과** — 관련 WebSocket 거부 테스트 3개는 통과했으나, 정지 사용자와 가능한 모든 DM 권한 조합을 별도 자동화하지 않았다.
3. 채팅 UI는 메시지를 HTML로 삽입하지 않고 `textContent`로 렌더링한다. **부분 통과** — 코드 검토는 완료했으나 실제 브라우저 DOM XSS 시연은 수행하지 않았다.
4. 사용자당 동시 연결 상한과 느린 수신자 fan-out 격리를 확인했다. **부분 통과** — `test_websocket_limits_concurrent_connections_per_user`, `test_slow_websocket_does_not_block_or_break_fanout`; 고부하 멀티프로세스는 미검증이다.

### FR-04 악성 사용자·상품 신고 및 차단

- 로그인 사용자는 사용자 또는 상품을 사유와 함께 신고할 수 있다.
- 동일 신고자가 같은 대상을 반복 신고해 임계값을 조작하지 못하도록 고유 제약을 둔다.
- 가입 후 10분이 지나지 않은 계정의 신고도 저장하지만 `auto_eligible=0`으로 두어 자동 제재 집계에서 제외한다.
- 임계값에 도달하면 상품은 `is_hidden=1`, `visibility_source='auto_report'`, 일반 사용자는 `status='suspended'`, `status_source='auto_report'`가 된다. 관리자 계정은 자동 정지하지 않는다.
- 관리자는 신고를 `actioned` 또는 `dismissed`로 판정한다. 기각 후 임계값 아래로 내려가면 출처가 `auto_report`인 제재만 복구하며, 출처가 `admin`인 수동 제재는 유지한다.
- 신고 사유는 서버에서 길이와 내용을 검증하고 화면에서는 이스케이프한다.

**인수 조건**

1. 상품·사용자 신고 저장과 신규 계정의 자동 집계 제외가 동작한다. **부분 통과** — `test_new_accounts_can_report_but_cannot_immediately_trigger_quarantine` 등으로 확인했으나 비회원 신고를 별도 테스트로 분리하지 않았다.
2. 동일 사용자·동일 대상 중복 신고는 409로 거부한다. **통과** — `test_duplicate_report_is_rejected_and_three_unique_reporters_quarantine_product`
3. 임계값 자동 숨김/정지, 기각 복구, 관리자 수동 제재 보존, 감사 기록이 동작한다. **통과** — `test_dismissal_releases_only_automatic_product_quarantine`, `test_dismissal_does_not_reverse_manual_product_moderation`, `test_dismissal_reactivates_only_auto_suspended_user`

### FR-05 사용자 간 가상 KRW 송금

- 인증된 활성 사용자는 다른 활성 사용자에게 정수 원 단위 금액을 송금할 수 있다.
- 자기 자신에게 송금할 수 없고, 금액은 최소 1원 이상, 설정된 1회 상한 이하여야 한다.
- 잔액 부족, 존재하지 않는 수신자, 정지된 송·수신자 요청은 거부한다.
- 출금과 입금 및 원장 기록은 하나의 SQLite 트랜잭션에서 원자적으로 처리한다.
- 동일 요청의 재전송으로 이중 송금되지 않도록 일회성 요청 토큰 또는 idempotency key를 사용한다.
- 성공 이체는 민감정보를 제외한 감사 이벤트로 기록한다. 검증 실패는 트랜잭션을 롤백하여 이체·원장 행을 남기지 않으며, 현재 별도 실패 감사 행은 생성하지 않는다.

**인수 조건**

1. 정상 이체 후 잔액 변화 합계가 0이고 이체 1건·원장 2행이 일치한다. **통과** — `test_transfer_moves_integer_balance_atomically_and_ledger_sums_to_zero`
2. 잔액 부족과 자기 송금은 부분 저장 없이 거부한다. **부분 통과** — `test_insufficient_balance_and_self_transfer_leave_no_partial_state`; 음수·0·소수·상한 초과의 모든 조합은 자동화하지 않았다.
3. 순차·동시 재전송과 서로 다른 병렬 송금에서도 중복 출금·마이너스 잔액이 없다. **통과** — 멱등성 및 병렬 송금 테스트 3개
4. 송신자는 요청 값이 아니라 세션 사용자로 고정한다. **통과** — 정상·실패·병렬 이체 테스트 전반에서 해당 경로를 사용하며 라우트는 `sender_id`를 받지 않는다.

### FR-06 상품 검색

- 비회원과 회원은 공개 상품의 상품명·설명을 키워드로 검색할 수 있다.
- 숨김·삭제·차단 상품은 일반 검색 결과에서 제외한다.
- 검색어 길이와 페이지 크기에 상한을 두고 페이지네이션한다.
- 쿼리는 ORM 또는 바인딩된 매개변수로 실행하며 입력을 SQL 문자열에 결합하지 않는다.

**인수 조건**

1. 정상 키워드와 결과 없음 검색이 동작한다. **부분 통과** — 검색 테스트는 있으나 한글·영문 경계를 분리해 자동화하지 않았다.
2. SQL 구문 모양의 검색어를 리터럴 데이터로 처리한다. **통과** — `test_search_treats_sql_syntax_as_literal_data`
3. 숨김 상품 필터와 검색 길이·페이지 상한을 구현했다. **부분 통과** — 자동 제재 상품의 비공개 동작은 확인했으나 반복 검색 부하는 자동 측정하지 않았다.

### FR-07 관리자 전체 요소 관리

- 관리자 전용 화면에서 사용자, 상품, 신고, 가상 이체 원장, 서비스 상태와 감사 이벤트를 조회한다.
- 사용자를 정지·복구하고 상품을 숨김·복구하며 신고를 승인·기각할 수 있다.
- 모든 관리자 변경은 대상, 행위, 시각, 관리자 식별자와 적용한 상태/판정을 감사 로그에 남긴다. 현재 일부 이벤트는 변경 전 상태 전체를 보존하지 않으므로 향후 감사 메타데이터 보강 항목으로 둔다.
- 일반 사용자는 관리자 URL을 알아도 접근할 수 없다.
- 원장 행을 임의 수정·삭제하는 기능과 별도 보정 기능은 제공하지 않는다. 향후 정정 기능을 추가한다면 기존 행 수정이 아니라 명시적인 보정 거래로 설계한다.

**인수 조건**

1. 일반 사용자의 관리자 대시보드와 사용자 상태 변경 접근을 거부한다. **통과** — 관리자 RBAC 테스트 2개
2. 관리자의 사용자 정지가 즉시 세션을 폐기한다. **통과** — `test_only_admin_can_change_user_status_and_suspension_revokes_sessions`
3. 상태 값은 허용 목록으로 검증하고 관리자 작업을 감사 로그에 남긴다. **부분 통과** — 사용자 상태 변경·감사는 확인했으나 모든 관리자 라우트의 변조 조합과 변경 전 상태 보존은 자동 검증·구현이 완전하지 않다.

## 6. 비기능 요구사항

### NFR-SEC 보안

- 모든 외부 입력은 신뢰하지 않고 형식·길이·범위·소유권을 서버에서 검증한다.
- 인증과 객체 소유권 검사를 분리하여 모든 변경 라우트에서 수행한다.
- 상태 변경 HTTP 요청은 CSRF 방어를 적용한다.
- Jinja2 자동 이스케이프를 유지하며, 사용자 입력에 `safe` 처리를 하지 않는다.
- 데이터베이스 질의는 매개변수 바인딩을 사용한다.
- 세션 쿠키는 `HttpOnly`, `SameSite`를 사용하고 운영 HTTPS에서 `Secure`를 사용한다.
- 비밀키와 운영 설정은 환경변수에서 읽고 저장소에 커밋하지 않는다.
- 상세 예외, SQL, 스택 트레이스, 비밀값은 사용자 응답과 로그에 노출하지 않는다.
- HTTP/WebSocket 모두 운영 환경에서 TLS(HTTPS/WSS)로 보호한다.
- 인증·송금·신고·관리자 기능은 행위별 속도 제한과 감사 로그를 적용한다.

### NFR-REL 신뢰성·무결성

- SQLite 외래키를 활성화하고 중요 상태 전이는 트랜잭션으로 처리한다.
- 모든 연결에 `journal_mode=WAL`, `busy_timeout=5000`, `synchronous=NORMAL`을 적용한다.
- 이체·신고 집계에는 유일성 제약과 원자적 갱신을 사용한다.
- 오류가 발생하면 부분 저장 없이 롤백하고 일반화된 오류를 제공한다.
- 백업과 복구 절차를 문서화했다. 실제 백업 복구 리허설은 **미검증**이다.

### NFR-PERF 성능

- 목록·검색·관리 화면은 페이지네이션하며 무제한 행 조회를 금지한다.
- 사용자명, 상품 상태·생성 시각, 검색 대상, 신고 대상, 원장 시각 등 주요 조회 열에 적절한 인덱스를 둔다.
- 일반 개발 환경의 자동 테스트에서 HTTP/WebSocket 핵심 흐름을 확인했다. 사용자당 WebSocket 3개·전체 80개 제한과 느린 클라이언트 격리는 자동 검증했으나, 실제 고부하 멀티프로세스 성능은 **미검증**이다.

### NFR-UX 사용성·접근성

- 오류 메시지는 사용자가 다음 행동을 알 수 있게 작성하되 계정 존재 여부나 내부 구현을 과도하게 노출하지 않는다.
- 폼에는 명시적 레이블과 서버 검증 오류를 제공하고 키보드로 핵심 흐름을 사용할 수 있어야 한다.
- 위험 작업은 대상과 결과를 명확히 보여 주고, 관리자 상태 변경에는 확인 단계를 둔다.

### NFR-MAINT 유지보수성

- FastAPI 라우터, 서비스, 데이터 접근, 템플릿, 정적 파일을 역할별로 분리한다.
- 환경설정·실행·테스트·초기 데이터 생성 방법을 README에 재현 가능하게 기록한다.
- 의존성 버전을 고정하고 GitHub Actions 워크플로를 구성했다. 로컬 기준 Ruff 통과, Bandit 이슈 0건, `pip-audit` 취약점 0건, `pytest` 36개 통과와 분기 커버리지 73%를 확인했다.

## 7. 범위 밖 항목

- 실제 화폐 충전·출금·결제·은행 및 카드 연동
- 계좌·카드·주민등록번호 등 고위험 개인정보 수집
- 배송, 위치 기반 직거래, 실명·성인 인증
- 다중 지역 고가용성, 대규모 트래픽, 모바일 네이티브 앱
- 종단간 암호화 채팅 및 법적 보존 시스템

범위 밖 기능은 누락이 아니라 과제 목적에 맞춘 위험 축소다. 향후 실제 서비스로 확장하려면 법률·개인정보·금융·운영 요구사항 분석을 새로 수행해야 한다.

## 9. 완료 판단

“화면이 존재한다”만으로 완료로 판단하지 않는다. 각 요구사항은 다음 네 증거가 모두 있어야 한다.

1. 구현 코드와 데이터 모델
2. 정상·경계·오류·권한·남용 테스트
3. 실행 결과 또는 수동 시연 기록
4. 발견한 보안 약점과 수정 전후 설명

현재 자동 검증 기준은 `pytest` 36개 통과(분기 커버리지 73%), Ruff 통과, Bandit 이슈 0건, `pip-audit` 취약점 0건이다. 실제 HTTPS/WSS 역방향 프록시, 백업 복구 리허설, 고부하 멀티프로세스는 완료 증거가 없으므로 계속 미검증으로 관리한다.
