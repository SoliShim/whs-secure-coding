# 시큐어 코딩 체크리스트

## 1. 판정 기준과 검증 범위

이 체크리스트는 강의 슬라이드 p.30~32의 요구사항·기능·보안 점검 항목을 현재 구현에 맞게 구체화한 것이다. 2026-07-22 로컬 검증 결과를 기준으로 작성했으며, 상세 명령과 테스트 이름은 [test-results.md](test-results.md)에 기록했다.

상태는 다음 의미로 사용한다.

- **통과**: 로컬 자동 테스트 또는 정적 검사와 코드 검토로 해당 통제의 핵심 판정 기준을 확인했다.
- **부분 통과**: 통제는 구현됐고 일부 증거가 있으나, 명시한 경계·동시성·다중 브라우저·운영 검증이 남았다.
- **미검증**: 실제 배포나 수동 환경이 있어야 판단할 수 있다.
- **실패**: 기대 결과와 다르며 제출 전 수정해야 한다.

`통과`는 현재 시험한 입력과 환경에서의 판정이지 “취약점이 전혀 없음”을 보증하지 않는다. 특히 로컬 HTTP 테스트는 HTTPS/WSS, 역방향 프록시, 운영 비밀, 백업 복구를 대신하지 않는다.

주요 증거:

- `tests/test_auth.py`: 가입·로그인·CSRF·Argon2id·쿠키·세션 폐기·XSS
- `tests/test_products_moderation.py`: 이미지 재인코딩·XSS·SQL injection·소유권·신고 격리
- `tests/test_security_websocket.py`: 헤더·일반화 오류·WebSocket 인증/Origin/CSRF·동시 연결 상한·느린 수신자 격리·전체/1:1 채팅
- `tests/test_wallet_admin.py`: 송금 원장·rollback·순차/병렬 멱등성·병렬 초과출금 방지·관리자 RBAC·세션 폐기
- `tests/test_hardening.py`: 익명 HMAC CSRF 쿠키·Content-Length/chunked 6MB 제한·과대 픽셀 이미지·신규 계정 신고 신뢰 대기·비밀번호 변경 제한·제재 출처와 안전한 복구
- Ruff, Bandit, pip-audit와 전체 테스트 실행 결과: `docs/test-results.md`

## 7. 잔여 위험과 수용 근거

- **Sybil 신고**: 한 계정의 중복 신고를 막고 가입 후 10분이 안 된 계정의 신고는 자동제재 집계에서 제외하지만, 미리 만든 여러 계정의 공모까지 신뢰성 있게 식별하지 못한다. 자동 조치는 임시 격리로 한정하고, 조치 출처를 기록해 관리자가 기각·복구하도록 했다.
- **단일 worker와 메모리 상태**: WebSocket은 사용자당 3개·전체 80개, 이미지 처리는 동시 3개로 제한하지만 연결과 rate limiter가 프로세스 메모리에 있어 재시작 시 제한 이력이 사라지고 다중 worker 간 공유되지 않는다. 과제 시연은 worker 1개로 제한하며, 확장 시 Redis 기반 공유 제한·pub/sub가 필요하다.
- **TLS 경계**: 애플리케이션은 production 설정을 강제하지만 인증서·TLS 종료·프록시 헤더 신뢰는 역방향 프록시 책임이다. 실제 공개 전 HTTPS/WSS 검증 없이는 운영 준비 완료로 판정하지 않는다.
- **SQLite와 로컬 파일**: 단일 인스턴스 교육용 규모에 적합한 구성이다. 고가용성, 다중 지역, 실제 금융 원장, 대규모 동시 쓰기를 보장하지 않는다.
- **테스트 범위**: 73% branch coverage와 병렬 송금·느린 WebSocket 회귀 시험은 핵심 경쟁 조건을 다루지만, 멀티프로세스 고부하·실제 TLS 프록시·장시간 soak test를 대신하지 않는다.

발견한 약점과 수정 내역은 보고서에서 원인, 악용 가능성, 수정 전후, 회귀 테스트까지 연결한다.
